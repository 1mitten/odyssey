# Lane A16 — Modding architecture beyond Defs, and the Z-Levels retrofit

## Question

How does RimWorld's modding architecture work in practice (beyond the Def/XML/patch mechanics already documented elsewhere), and what does the Z-Levels mod's experience teach about bolting discrete vertical layers onto an engine that was built 2D-first?

Clean-room note: everything below is restated from public documentation, community write-ups and the **Z-Levels mod's own source** (`github.com/RamRod6198/Z-Levels`, MIT-style community mod, read for architecture per the brief's explicit sanction of that repository — never copied, only described in our own words). No RimWorld engine code, decompiled or otherwise, was read or is reproduced here.

## Findings

### 1. What modders reach for in Harmony

**The three ordinary patch shapes.** A prefix runs before the original method, can read and rewrite its arguments, and — by returning `false` — can cancel the original body outright; a postfix runs after and is guaranteed to run, can rewrite the return value (`ref __result` and named `___field` accessors reach private state), and is the shape the community treats as "safest" because it never suppresses another mod's prefix. A transpiler rewrites the method's IL directly via `CodeInstruction` sequences and is reserved for changes a prefix/postfix genuinely cannot express (altering a loop bound or an inlined constant deep in a vanilla method body); it is explicitly documented as hard to write, hard to review and hard to keep working across game updates, because it depends on the exact shape of decompiled IL. A fourth shape, the **finalizer**, wraps the original call in try/catch semantics — the documented use is suppressing or rewriting an exception a vanilla method would otherwise throw, which lets a mod treat "the base game did something this mod doesn't expect" as a recoverable condition instead of a crash.
Sources: https://gist.github.com/EliteMasterEric/cc9f0271af9410aec32ead637efe7741, https://harmony.pardeike.net/v2/articles/patching-transpiler.html, https://rimworldwiki.com/wiki/Modding_Tutorials/Harmony, https://rimworldwiki.com/wiki/Modding_Tutorials/HarmonyTranspiler

**What gets patched, in practice, is whatever a Def field cannot reach: control flow and cross-cutting state.** The Z-Levels source (read directly — see §2) is a representative sample of a mod that patches nothing at the content level and everything at the control-flow level: sixteen patch files covering reachability and reservations, jobs, the float (right-click) menu, combat targeting, the colonist bar, trade, weather, wealth calculation, roofs and floors, skyfallers, animals and the resource counter — none of which is expressible as Def data, because each is a piece of *logic* (a method body) that assumed a single fixed context (one map, one reachability grid, one power net) and needed that assumption removed at the call site. This matches the general community pattern: Defs configure content, Harmony changes behaviour, and a mod that needs new behaviour with no vanilla hook reaches for Harmony almost by default.
Sources: `RamRod6198/Z-Levels` source tree (`Source/ZLevels/ZLevels/HarmonyPatches/`), read directly, September 2026.

**What makes a class or method easy or hard to patch.** Confirmed constraints, cited directly: **a sealed class cannot be patched by Harmony at all** — there is no subclassing escape hatch the way there is in ordinary C#, since Harmony patches the original method's IL in place rather than substituting a derived override. **Private members are reachable but at a cost**: `AccessTools`/`Traverse` gives reflective access to private fields and methods, but the community's own profiling found that using `Traverse` inside a patch that runs every tick added measurable overhead (reported as tens of milliseconds against a fraction of a millisecond for a direct field-reference patch), which is why the documented convention for a hot-path private field is `AccessTools.FieldRefAccess<T>` — a cached delegate built once, not a `Traverse` call repeated every tick. **Static caches are the recurring silent hazard**: a method that reads state cached in a static field or a static constructor computes something once and expects it to stay valid; patching the method without also accounting for when that cache was populated (or invalidating it) produces a patch that appears to work until the cache goes stale, which is exactly the class of bug Z-Levels' own comments show it fighting (see `MapComponentZLevel`'s half-finished `hasCavesBelow` nullable-cache field and commented-out generation logic, §2).
Sources: https://harmony.pardeike.net/v2/articles/intro.html (sealed-class limitation, cited via search excerpt since the domain is proxy-blocked — see Could not be determined), https://github.com/pardeike/Harmony/issues/289 (Traverse performance cost), general AccessTools documentation surfaced via the same search.

**Documented conventions the modding community follows to stay patchable, and that the base game is asked to follow.** One `HarmonyPatch`-attributed class per patched method, named for what it does rather than for the method it targets, so a shared debug log ("HugsLib publishes a log of every patch on request") is legible to someone reading it who is not the patch's author. Patch bodies are static methods; the attribute names the target by `typeof` and either a string method name or `nameof`, with an explicit `Type[]` overload list when the target is overloaded — the wiki's own transpiler tutorial exists largely because ordinary attribute matching under- or over-selects when a method is generic, overloaded or a property accessor. A widely cited convention from the framework-mod ecosystem (HugsLib, and by extension the Vanilla Expanded framework) is: **do not write your own Harmony bootstrap and log if a shared library already provides one** — a mod should attach to an existing patch-management and logging surface rather than duplicating it, because duplicated Harmony instances are a common source of load-order-sensitive bugs. On the base game's side, the CLAUDE.md rule we already carry (**public, unsealed, virtual where cheap**) is the mirror image of the sealed-class and static-cache hazards above: RimWorld itself is not sealed anywhere that matters to modders, and its own classes' methods are non-static instance methods on ordinary (non-static) manager objects reachable from `Map`/`GameComponent`, which is precisely what makes prefix/postfix patching against it tractable at all.
Sources: https://github.com/UnlimitedHugs/RimworldHugsLib/wiki/Introduction-to-Patching, https://github.com/UnlimitedHugs/RimworldHugsLib, https://rimworldwiki.com/wiki/Modding_Tutorials/HarmonyTranspiler

### 2. The Z-Levels mod

**What it adds.** Z-Levels lets a player dig a level below their base or build a level above it, each reachable by an in-game stair, with a UI control to switch which level is currently rendered and interactive. It is explicitly a beta with a public bug list and depends on the community's shared Harmony loader mod.
Sources: `RamRod6198/Z-Levels/About/About.xml` (mod manifest text, read directly)

**How it represents multiple levels — the central architectural fact.** Z-Levels does not add a third grid axis to the map. **Each level is a separate, independent `Map` object**, wrapped in a `MapParent_ZLevel` that subclasses RimWorld's `MapParent` — the very class the base game uses to represent an off-map world location (a settlement, a caravan site) that the player's home map can travel *to*. In other words, the retrofit's foundational move is to treat "the level below your base" as if it were a **separate place on the world map**, linked to the surface map the same way a second settlement would be, not as a slice of one 3D volume. A `MapComponentZLevel` companion tracks a per-map z-index, a "has caves below" flag, and per-map infestation state; a global `ZTracker` singleton maps world-map tiles to their stack of level `Map`s and indexes each pawn's in-flight cross-level job state (`jobTracker`). Every one of the "twelve layer questions" this project asks — is a roof a floor, do rooms span layers, can you shoot up and down — has to be answered again from scratch under this model, because vanilla's per-`Map` systems (reachability, rooms, weather, fog of war, power nets) know nothing of the other `Map`s stacked on the same tile.
Sources: `RamRod6198/Z-Levels/Source/ZLevels/ZLevels/Map/MapParent_ZLevel.cs`, `MapComponentZLevel.cs` (read directly)

**How movement between levels actually works: teleport-and-patch, not unified pathing.** A pawn walking from one level to another runs a bespoke `JobDriver_GoToStairs` → `JobDriver_GoToMap` pipeline (`Toils_ZLevels.GoToMap`) that, at the moment of transition, **relocates the pawn's `Map` reference outright** (`ZUtils.TeleportThing`) rather than computing one continuous path through a 3D grid. Because vanilla's reachability and reservation queries (`Reachability.CanReach`, `ReservationManager.CanReserve`, `CanReserveStack`) are hard-coded to operate against the querying pawn's *current* `Map`, any cross-level query has to be faked: the patch **teleports the pawn to the destination map, asks vanilla's own single-map reachability/reservation code the question, reads the answer, and teleports the pawn back** before returning control — visible directly in `ReachAndReservationPatches.cs`'s `CanReach_Patch` and `ReservationManager_CanReserve_Patch`, each of which stores `oldMap`/`oldPosition` in a prefix and restores them in a postfix around a single vanilla call. The same teleport-query-restore idiom recurs in combat target-finding (`CombatPatches.cs`: `BestAttackTarget` is re-entered once per level, walking the pawn to each level's `Map` in turn to ask "is there a target visible from here") — there is no single query that reasons about all levels at once; the mod instead calls vanilla's single-map logic *n* times, once per level, wrapped in enough bookkeeping to look atomic from outside.
Sources: `RamRod6198/Z-Levels/Source/ZLevels/ZLevels/HarmonyPatches/ReachAndReservationPatches.cs`, `Jobs/JobDriver_GoToMap.cs`, `HarmonyPatches/CombatPatches.cs` (read directly)

**Line of sight is a documented compromise, not a solved problem.** The occlusion check `GenGrid.CanBeSeenOverFast` is patched so that, whenever a cross-level shot is being evaluated (`checkLevels == true`), the function **returns `true` unconditionally** in the fast path before falling through to a narrower special case — i.e. normal wall/height occlusion is bypassed rather than re-derived in 3D for the cross-level case. This is the sharpest concrete evidence in the source that faithful 3D line of sight was judged too expensive or too invasive to retrofit, and a coarser approximation was substituted instead.
Sources: `RamRod6198/Z-Levels/Source/ZLevels/ZLevels/HarmonyPatches/CombatPatches.cs` (`CanBeSeenOverFast_Patch`, read directly)

**Rendering is a 2.5D illusion, hand-tuned per thing type, not a real depth buffer.** There is no unified 3D draw pass. Instead, a postfix on `DynamicDrawManager.DrawDynamicThings` iterates every *other* level's `Map`, and for each thing on it, redraws that thing over the current view with a manually tuned draw-position offset and a shrunk sprite scale to fake parallax depth — separate, hand-picked constants (`[TweakValue]`-adjustable) exist for turrets, motes, pawns and generic things, and pawns, corpses and doors each needed **their own separate case** because the generic offset-and-rescale trick doesn't apply to their draw code (a code comment on the pawn case reads "`TODO Transpile PawnRenderer`" — acknowledged as unfinished). Separate `SectionLayer_LowerFogOfWar` / `SectionLayer_LowerTerrain` / `SectionLayer_LowerThings` classes exist purely to mesh-render "the level below" as a background layer under the active one. `Thing.DrawPos`, `Mote.DrawPos` and `GenThing.TrueCenter` all needed postfix patches to add a global z/y offset when this fake-depth draw pass is active. **This is the single clearest lesson for Odyssey**: retrofitting depth onto a renderer that assumes one flat map per draw call means faking depth per-thing-type by hand, forever, rather than depth being a property of the world representation itself.
Sources: `RamRod6198/Z-Levels/Source/ZLevels/ZLevels/MapRenderer/RenderPatches.cs`, `SectionLayer_Lower*.cs` (read directly)

**Systems that are inherently "one per map" in the base engine, and the parallel structures Z-Levels had to build to bridge them.** Power nets (`PowerNet`) are computed per `Map`; a machine on one level cannot naturally belong to the same net as one on the level above. Z-Levels' answer is a wholly separate shadow network — `ConnectedPowerNets` / `ConnectedPowerNet` — that groups the mod's own bridging component (`CompPowerZTransmitter`) across maps by proximity, ticks itself from a **postfix on `World.WorldPostTick`** (the world-level tick, not any one map's tick, because the whole point is that it must run regardless of which single map is currently loaded/active), and redirects `PowerNet.CurrentStoredEnergy` reads through a prefix so the vanilla UI reports the pooled total. The same "vanilla assumed one map, so build a second bookkeeping structure beside it and patch the read paths to consult it" pattern recurs for wealth (a colony's wealth score is naturally a per-map sum), the resource counter, and the colonist bar (which must list pawns physically standing on several different `Map` objects as if they were one colony's roster).
Sources: `RamRod6198/Z-Levels/Source/ZLevels/ZLevels/PowerTransfer/ConnectedPowerNets.cs` (read directly); file names and scope inferred from `HarmonyPatches/WealthPatches.cs`, `ResourceCounterPatch.cs`, `ColonistBarPatches.cs` (read via directory listing and partial read, not fully read line-by-line — see Could not be determined)

**Scale of the patching effort, as a concrete number.** The sixteen Harmony patch files in Z-Levels' source total **6,621 lines**, dominated by `JobPatches.cs` (2,408 lines, plus a 717-line `JobPatches - Copy.cs` left in the tree — itself a sign of an unfinished refactor) and `FloatMenuPatches.cs` (971 lines, because every right-click context action needs to know which map the thing under the cursor actually lives on when "the cursor" can be looking at a rendered-through-fake-depth thing on a different level entirely — see the `LocalTargetInfo` constructor patch in `ReachAndReservationPatches.cs`, which exists solely to remember which map a clicked cell "really" belonged to). This is offered as a proxy for retrofit cost, not a precise LOC-to-effort ratio: it is what "teach every map-scoped subsystem about other maps, one call site at a time" costs in a codebase not designed for it.
Sources: line counts taken directly from the cloned repository, September 2026.

**What is left half-finished, in the source's own words.** `MapComponentZLevel` carries commented-out settlement/generation code, an unused `path` string field, and a nullable `hasCavesBelow` field computed twice with duplicated logic — read together, these are marks of a system still being iterated on rather than a settled design, consistent with the mod's own "BETA, might have issues" disclaimer and its documented known bug (a "natural hole" structure players are told to avoid entirely because it can only be used correctly by the mod's own infestation generator).
Sources: `RamRod6198/Z-Levels/Source/ZLevels/ZLevels/Map/MapComponentZLevel.cs` (read directly); `About/About.xml`

**Incompatibilities and the community's response.** Community sources describe Z-Levels as eventually abandoned and effectively unmaintained relative to current RimWorld versions, with a documented incompatibility against the "Colonist Bar KF" mod (both patch the same colonist-bar drawing surface) and load-crash reports (a shared bug report shows unresolved `Map` cross-references and null-reference exceptions inside the mod's own `AdjustMapGeneration` and `TeleportPawn` methods when loading a save alongside a large mod list — i.e. the multi-`Map`-plus-teleport model is fragile exactly at its two structural joints, world-save serialisation of extra `Map`s and the teleport call itself). Rather than being fixed, Z-Levels was **superseded by at least three independent successor mods** — "MultiFloors" (described by the community as a spiritual successor built for better performance and compatibility), "Z Pocket Dimension", and "DeepRim" — which is itself a data point: the community's verdict on the original retrofit was to start over with a narrower scope rather than continue patching it.
Sources: search-engine synthesis of https://steamcommunity.com/sharedfiles/filedetails/comments/2127428910, https://rimworldbase.com/z-levels-mod/ and related listings (both domains are proxy-blocked for direct fetch in this environment — content below is as reported by the search tool's own summarisation, treated as medium confidence — see Could not be determined); https://gist.github.com/Zylleon/85c01ad72c546cd4bc09c24cba8bb3be (a shared crash-log gist, fetched directly, showing the `Map` cross-reference and `TeleportPawn`/`AdjustMapGeneration` null-reference failures)

### 3. General modding-ecosystem lessons

**Load order is explicit, user-controlled, and mods declare constraints on it rather than trusting a default.** A mod's manifest can declare `loadAfter`/`loadBefore` relationships and dependencies (Z-Levels' own manifest declares `loadAfter` on the core game, the Royalty DLC and its Harmony dependency); large framework mods go further and publish a recommended position "as close to Core as possible" because they provide services (a shared Harmony instance, shared UI widgets, shared generation code) that many other mods build on and therefore must be initialised first.
Sources: `RamRod6198/Z-Levels/About/About.xml`; community load-order guidance summarised from search results citing Vanilla Expanded Framework placement advice.

**Compatibility-patch culture is a first-class, expected activity, not an edge case.** Large gameplay-overhaul mods (Combat Extended is the paradigm case) publish their own compatibility-patch authoring guide, because the community norm is that the overhaul's author cannot patch every other mod pre-emptively — instead a documented extension surface (specific classes and stats the overhaul expects other content to expose) lets third parties write bridge patches. `PatchOperationLoadDefsOnDemand` is one such community-contributed shared operation, built specifically to smooth over load-order-sensitive patch failures. This is the ecosystem-level mirror of the AddModExtension mechanism already recorded in `d-07-data-pipeline.md`: the base game and its biggest mods both converge on "declare a stable surface, let others attach to it" over "everyone patches everyone."
Sources: https://github.com/CombatExtended-Continued/CombatExtended/wiki/Compatibility-Patch-Guide, https://steamcommunity.com/sharedfiles/filedetails/?id=1758482195 (compatibility-patch guide summarised via search)

**Total-conversion-scale mods are structured as a shared framework plus thin leaf mods, not as one monolith.** The Vanilla Expanded family separates a single "Vanilla Expanded Framework" library — custom gizmos, hediff mechanics, base-generation code, faction/apparel systems, shared UI — from dozens of independent content mods that depend on it. The framework is explicitly designed to be usable by mods outside the family too. This is the same "shared library, many thin dependents" shape as `RimworldHugsLib`, and the ecosystem's own stated reason for it is to avoid duplicating Harmony patches and logging/settings scaffolding across many mods that would otherwise all patch the same handful of vanilla methods independently and step on each other.
Sources: https://github.com/Vanilla-Expanded/VanillaExpandedFramework, https://github.com/Vanilla-Expanded/VanillaExpandedFramework/wiki/, https://github.com/UnlimitedHugs/RimworldHugsLib

## Recommendation

1. **Ship one first-class extension seam for "another simulation object wants to know about this cell/pawn/network across a layer boundary" before any mod ever needs Harmony to fake it.** Z-Levels' entire cost centre — the 6,600 lines of patches, the teleport-query-restore idiom, the shadow power-net structure — exists because RimWorld's per-map managers (`Reachability`, `ReservationManager`, `PowerNet`, the wealth/resource counters, the colonist bar) were never given a parameter for "which layer/place are we asking about"; a modder had to invent one from outside by temporarily lying to the object about its own context. Odyssey's grid, pathfinding, reservation, network and room systems must take a layer-aware key **as a normal parameter from their first signature**, per the brief's non-negotiable #2, specifically so that no future modder (or future Odyssey subsystem) ever needs the teleport-and-restore trick to ask a cross-layer question.

2. **Never represent a layer as a separate top-level "place" object the way Z-Levels represents a level as a separate `MapParent`.** That single design choice is the root of nearly everything documented in §2: fog of war, weather, reachability, rooms and power all come "free" only within one such object, so every one of those systems had to be re-taught about siblings. Odyssey's plain-C#-SoA world (ADR 0005) already stores cells in one addressable (x, y, z) space; the discipline this research adds is to **keep every subsystem's public API keyed by a full 3D coordinate or cell handle, never by a bare (x, y) pair plus an implicit "current layer"**, so there is never a hidden single-layer assumption for a future patch to work around.

3. **Do not let rendering depth be a per-thing-type hand-tuned illusion.** Z-Levels' draw offsets, separate pawn/corpse/door/turret cases and the frank `TODO Transpile PawnRenderer` are the clearest single failure mode in this research: depth was not a property of the scene, so it had to be faked per object kind, and the fakery was still incomplete after years of development. Odyssey's cut-away camera and instanced-rendering plan (`docs/design/06-rendering-and-camera.md`) already treats layer as a real spatial coordinate; this research is a concrete argument for keeping that discipline rather than ever special-casing "how does thing type X look when the view is one layer below it," which is exactly the trap the retrofit fell into.

4. **Keep sim classes public, unsealed and virtual where cheap (already the rule) — and additionally, avoid static caches on anything a modder might need to invalidate.** Z-Levels' own half-finished nullable-cache field (`hasCavesBelow`) and the community's documented "sealed classes can't be patched at all" / "static caches are the silent hazard" findings both point the same direction: prefer instance state reachable from a composition root over static state, exactly as `d-07-data-pipeline.md` already commits to for the Def system (`DefSet` owned by the composition root, never a static). Extend that same rule to every runtime manager we write for layers, networks and reservations.

5. **Publish one shared extension/compat surface rather than expecting third-party patches against internals**, mirroring the Vanilla Expanded Framework / HugsLib pattern and the Combat Extended compatibility-guide culture: when the scripting API lands at M8 (per the brief), it should expose the layer-aware hooks a mod would otherwise need Harmony for (a cell/thing query that already takes a layer, a job/reservation system a mod can subscribe to rather than patch, a documented "this is where you attach cross-cutting data" mechanism analogous to `AddModExtension`). This converts the single largest cost this research found — an ecosystem-wide scramble to patch every map-scoped method by hand — into a designed seam instead.

**Tie-break, stated explicitly:** where recommendation 1 (parameterise every subsystem by layer) and recommendation 5 (publish a scripting surface later) could be read as redundant, the tie-break is timing, not substance: recommendation 1 is a Phase 4/M0–M2 architectural discipline with no scripting API required, while recommendation 5 is the M8 payoff of having kept that discipline. Do 1 now; 5 becomes cheap specifically because 1 was done.

## Layer questions touched

- **Q1 (vertical movement/pathing):** Z-Levels' teleport-query-restore idiom around `Reachability.CanReach` is direct evidence that per-map reachability grids cannot answer a cross-layer question without being lied to about their own context; Odyssey's pathfinding (already flagged as the top technical risk) should treat layer as a native dimension of the search space, not a second map to hop between.
- **Q3 (do rooms span layers, does heat rise):** the shadow `ConnectedPowerNets` structure and the wealth/resource-counter patches show that "sum this per-map quantity across the stack" is exactly the shape of problem rooms-across-layers and heat-across-layers will also pose; the retrofit's answer (a parallel bookkeeping structure bridging otherwise-isolated per-map systems) is the pattern to avoid by designing rooms/heat as inherently 3D from the start.
- **Q5 (line of sight in 3D):** the `CanBeSeenOverFast` patch that returns `true` unconditionally for cross-level shots is a documented case of a retrofit choosing to skip real 3D occlusion rather than solve it; this is the concrete cautionary case for whatever line-of-sight model Odyssey's combat research settles on.
- **Q9 (camera slicing and UI):** the entire rendering-patches picture in §2 (fake parallax offsets, per-thing-type special cases, the unfinished pawn-renderer transpile) is the strongest evidence in this file that a cut-away/slice camera must be built into the renderer's data model from the start, not layered on afterward.
- **Q10 (unit of simulation for gas, fire, water and sound across layers):** touched indirectly by the power-net bridging pattern; the same "vanilla assumed one contiguous network per map" problem will recur for gas/heat networks if Odyssey ever lets a single network's cells span layers without that being native to the network's own addressing.
